# pricelock

**Bake point-of-sale-accurate prices into a static site at authoring time — keyed by catalog item id, with a committed snapshot and an offline parity gate.**

This is a reference implementation — *show-your-work*, not a product. It is the working proof behind [**"What the all-in-one ordering platforms don't tell independent restaurants"**](https://10ustech.com/insights/restaurant-ordering-platform-lock-in) on the 10 US Tech Inc. Insights blog. Read that piece for the argument; read this repo for the mechanism.

It runs credential-free on bundled demo data:

```bash
node bin/bake-prices.mjs --check   # is the committed site in sync with the catalog?
node --test                        # offline parity gate: visible == JSON-LD == snapshot
```

No install step, no dependencies, no tokens, no database.

---

## The problem: price drift

A restaurant runs a fast static/Jamstack site *and* a point-of-sale system (Square, here). The POS is the real source of prices. The static site has prices typed into HTML. The two drift apart the moment someone changes a price at the register — the site quietly shows yesterday's number, and so does every price a search engine or AI assistant reads out of the page.

The three obvious fixes each fail:

- **Edit the HTML by hand every time a price changes.** It doesn't scale, and it silently rots — nobody re-types a menu the day a price moves.
- **Move onto an all-in-one ordering platform.** It ends the drift by taking the site, the SEO surface, and the customer relationship with it — the lock-in the Insights piece is about.
- **Fetch prices live from an API at request time.** Now every page view — and every deploy that seals the site — depends on the POS being reachable, and the price isn't in the HTML a crawler indexes.

## The approach: bake at authoring time

Fetch the catalog once, on your machine, and **write the correct price into the committed HTML** — both the visible node and the JSON-LD. The published site is plain static files; nothing is fetched at request time. When a price changes at the register, you re-run the baker, commit the diff, and ship.

```
POS catalog ──(authoring time, once)──▶ bake-prices ──▶ committed HTML (visible + JSON-LD)
                                                    └──▶ prices.snapshot.json  (trust anchor)
```

## The landmine: key by item id, never by display name

This is the bug that bites everyone who builds this the quick way.

Two menu items can share a **display name** and cost **different amounts** — a lunch/dinner twin. In the demo catalog, *House Salad* is **$12 at lunch** and **$16 at dinner**: two distinct catalog objects, two ids, one name.

Build a `{ name → price }` map and you get **last-wins**: whichever *House Salad* the loop sees last overwrites the other, and half your menu is silently mispriced. Nothing errors. The page looks fine. The number is just wrong.

So every price node is anchored to the stable catalog **id**, not its name:

```html
<div class="item-price" data-sq-item="HOUSESALADLUNCH0000000001">$12.00</div>
```
```json
{ "@type": "MenuItem", "name": "House Salad", "identifier": "HOUSESALADLUNCH0000000001",
  "offers": { "@type": "Offer", "price": "12.00", "priceCurrency": "USD" } }
```

Once a node carries its id, it is priced by that id forever — unambiguous. The only place names are used is to *attach* an id to a brand-new, still-unanchored row, and there the resolver **fails closed**: if a name maps to more than one catalog object and neither the current price nor the section disambiguates it, the baker throws and writes nothing rather than guess.

## The trust anchor: a committed snapshot + an offline gate

`bake-prices --write` also emits `demo/prices.snapshot.json` — a sorted `{ id → { name, price } }` record of exactly what was baked. `test/parity.test.js` then proves, **with no catalog and no network**, that for every id the three surfaces agree:

> visible price  ==  JSON-LD price  ==  snapshot price

Edit any single price without resealing the snapshot and the gate fails. That is what makes the baked prices **tamper-evident**: the snapshot is the thing a reviewer (or CI) diffs against, offline, forever.

`.github/workflows/ci.yml` runs both the drift check and the parity gate on every push.

## Files

| Path | What it is |
|---|---|
| `bin/bake-prices.mjs` | The baker. `--check` (no write) / `--write` (rewrite in place). |
| `demo/catalog.json` | A neutral demo catalog in the public Square Catalog shape, including the name-collision twin. |
| `demo/site/menu.html` | A demo static page: visible prices + JSON-LD, every node anchored by id. |
| `demo/prices.snapshot.json` | The committed trust anchor (generated by `--write`). |
| `test/parity.test.js` | The offline parity gate. |
| `.github/workflows/ci.yml` | Drift check + parity gate in CI. |

## Using your own catalog

Point `--src` at any catalog in the same shape — a file, or a URL that returns it:

```bash
node bin/bake-prices.mjs --write --src ./my-catalog.json --site ./public --snapshot ./public/prices.snapshot.json
```

The demo reads a **public, credential-free** catalog endpoint pattern. It never needs an access token, and there is deliberately **no** `.env`, no secret, and no committed real catalog anywhere in this repo. Keep it that way: bake from a public read pattern, commit only prices — never keys.

Catalog shape:

```json
{
  "cachedAt": "2026-01-01T00:00:00Z",
  "menu": [
    { "name": "Lunch",  "items": [ { "id": "…", "name": "…", "price": 12.00 } ] },
    { "name": "Dinner", "items": [ { "id": "…", "name": "…", "price": 16.00 } ] }
  ]
}
```
