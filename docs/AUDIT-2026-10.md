### Checked and not a finding

- **DNS rebinding** — `guardedLookup` re-checks at connect time; the existing test covers a public→loopback flip. Node skips `lookup` for IP literals, which `assertPublicHost` already checked. Sound.
- **Redirects, credentials in URL, non-https, numeric-form hostnames** (`https://2130706433/`) — the WHATWG parser normalises to dotted decimal before the blocklist sees it. Sound.
- **Prototype pollution via feed ids** — ids are `^[A-Z0-9]{20,}$`, so `__proto__` cannot be a snapshot key. Catalog names are never written to HTML.
- **Regex backtracking** — the tempered-lookahead patterns are linear per candidate; pages are small. Not a practical concern.
- **Ambiguity / missing-id fail-closed, in-memory bake before write** — as documented; tests confirm.
- **Concurrent bakers** — uncoordinated by design; the tree is a git working copy. Documented, not fixed.

## Phase 4 decision: no versioned publisher

The brief asked whether crash-safe, versioned publication belongs here. It does not. The baker
does not publish: it rewrites a git working tree that the operator then commits, and the
site's own build deploys the commit. Git already provides immutable versions, atomic switch
(the commit), previous-release tracking and rollback (`git checkout`, `git revert`). Adding a
release directory, lock and rollback command would duplicate that inside a reference
script and invite the operator to bypass the commit. What *was* missing is per-file
atomicity (F9), which is now provided. The README's "Writes and recovery" states exactly
what is and is not guaranteed: atomic visibility per file, process-crash recovery via git,
**no** power-loss durability claim (file data fsynced, directory entry not).

## Open decisions (owner)

1. **Make `--strict` the default?** CI uses it; the CLI default is still WARN so existing
   README behaviour holds. Flipping the default is a one-line change plus the `warn`
   fixture test. Recommended once any real site has been baked under `--strict` cleanly.
2. **Require both surfaces per id?** The parity check could insist every snapshot id has a
   visible node *and* a JSON-LD entry. Not done: a site may legitimately list an item only
   in structured data. Easy to add if the estate's pages always carry both.

## Remaining risks and unverified assumptions

- F7 and F9 are verified at the unit level (bounded reader, atomic writer) and by code
  inspection of the call sites; no live HTTPS server or kill-mid-write harness was built.
- Power-loss behaviour is asserted from POSIX semantics, not tested.
- `--strict` has been run against the demo only. A real site may surface legitimate
  `$`-bearing copy ("from $5") that it will refuse; that is the intended trade.
- Node 18.17.0 and 20 were not executed locally (22 only); CI covers the matrix. The code
  added uses no API newer than 18.17 (`net.BlockList`, `fs.lstatSync`, `fsyncSync`).
