# Correctness audit — 14 November 2026

**Scope:** `10USTECH/pricelock` at `main@025b885` (v1.4.0).
**Trigger:** an external source-level handoff listing five suspected correctness failures
(identity assignment, JSON-LD property collisions, attribute-name case, `@id` graph merging,
inert HTML). It asked for each to be reproduced or disproven, not assumed.
**Method:** each probe mutated a scratch copy of the repo's demo and ran exactly what CI
runs — `node bin/bake-prices.mjs --check` and `node --test test/parity.test.js` (after
`--write` where the scenario is a first bake). MISSED = both gates pass. Every MISSED row is
a test in `test/audit-2026-11-14.test.js`, committed failing (16 of 20) before any fix.

## Findings

| # | Handoff severity | Result at 025b885 | Class | Severity here |
|---|---|---|---|---|
| F1 | High | **Confirmed.** Unanchored twins showing each other's price: `--write` exits 0 and anchors the Lunch row to the Dinner id on both surfaces; `--check` and parity then pass. | defect | **High** |
| F2 | High | **Confirmed, and wider than reported.** A second price under `https://schema.org/price`, `http://schema.org/price` or `schema:price` passes both gates. So does a local `@context` that aliases any term to price — which no list of keys can catch. | defect | **High** |
| F3 | High | **Confirmed, lower impact.** `DATA-SQ-ITEM="A" data-sq-item="B"` passes both gates; a browser keeps A, the baker read B. | defect | Low |
| F4 | High | **Partly mitigated already.** A second node sharing an `@id` that adds an offer with `price` or `priceCurrency` was already refused (v1.4 R3 / unread-price report). It passed only when the price was spelled `schema:price` (i.e. through F2). | mitigated + F2 | Low alone |
| F5 | Medium | **Confirmed.** The whole visible menu inside `<!-- -->` or `<template>` passes both gates (the page renders no prices). An ld+json block inside a comment was baked as live — documented in v1.4, now refused. | defect / was accepted limitation | Medium |

### Where the handoff was wrong or incomplete

- **F1** does not need both rows swapped by an attacker in general, but it is narrower than
  "any stale page": a single stale twin (`Lunch 12→16, Dinner 16→18` in the catalog) was
  already **refused** at 025b885, because the JSON-LD side had no section and hit the
  ambiguity error. The pass needs every twin's page price to equal exactly one candidate —
  a swapped pair, or a copied row.
- **F2's example key is the weakest of the three.** The published schema.org context maps
  terms to `http://schema.org/`, so to a strict JSON-LD processor `https://schema.org/price`
  is a *different* property from `price`. `http://schema.org/price` and `schema:price` are
  the exact collisions. Consumers that treat both schemes alike read all three.
- **F3 is not High.** Nothing but pricelock reads `data-sq-item`; the visible price does not
  change. It matters only to script that reads the attribute. Fixed anyway (one flag).
- **F4** as written ("without another literal price property") leaves a second offer with no
  price — a malformed offer, not a second price.
- **Missed by the handoff:** the `@context` alias (F2), and N1 below.

## Fixes (v1.5.0)

| # | Fix | Why this and not more |
|---|---|---|
| F1 | `resolveUnanchored` uses the section only (visible: `<h2 class="cat-title">`; JSON-LD: nearest enclosing `MenuSection` name). The page price is never a tie-break. No unique section → refused; add the id by hand. | The page price is the untrusted value. Requiring explicit ids for every duplicated name would break the first-bake of a sectioned menu for no gain. |
| F2 | `assertPlainSchemaOrg` (baker and parity extractor): every ld+json block must use plain terms — `@context` only at the top and only `http(s)://schema.org[/]`, no key containing `:`, keywords limited to `@context @type @id @graph @value @language @list @set`. | An allowlist is the only complete answer to aliasing. A JSON-LD processor would be a dependency and a much larger surface. |
| F3 | The anchor count is case-insensitive; the accepted form stays one lowercase `data-sq-item="…"`. | — |
| F4 | A managed MenuItem or its Offer carrying `@id` is refused. | Matching `@id`s is unreliable (relative vs absolute IRIs resolve to the same node). An anonymous node cannot be merged into. |
| F5 | `inertRanges`: comments and the bodies of `<template>`, `<noscript>`, `<textarea>`, `<title>`, `<style>`, `<xmp>`, `<iframe>`, `<noembed>`, `<noframes>` and non-JSON-LD `<script>`. A price node or ld+json block inside one is **refused** by the baker and the parity extractor. | Refusing (not skipping) means a disagreement between this pattern scan and a real HTML parser fails closed. |

## Behaviour changes (each fails closed)

- An unanchored twin outside a section, or twins within one section, that the page price
  used to disambiguate now needs a hand-written id. `test/hardening.test.js` "V2: price
  tie-break" was rewritten to assert the refusal.
- Valid JSON-LD that uses a custom or array `@context`, prefixed keys, `@reverse` / `@nest` /
  `@included`, or an `@id` on a managed item or offer is refused on any page under `--site`.
- A commented-out price row or ld+json block stops the run instead of being baked.

Unchanged: the feed contract, zero dependencies, byte-for-byte output on an already-correct
page (the demo tree and snapshot are untouched by this change).

## New limitation found (documented, not fixed)

- **N1 — an anchored id is trusted; its name is not checked.** Swapping the ids of the
  Garden Salad and Tiramisu rows passes both gates: each row shows the other item's price
  under its own name. Comparing the displayed name to the catalog name would refuse every
  site whose menu wording differs from its POS wording, so this is an owner decision, not a
  patch. Recorded in `GUARANTEES.md`.
- Inert-region detection is a pattern scan; `hidden`, CSS and closed `<details>` are treated
  as live.

## Result

141 tests pass (121 before; 20 added, 1 rewritten). `bake-prices --check` on the demo:
exit 0, no file would change, snapshot unchanged.
